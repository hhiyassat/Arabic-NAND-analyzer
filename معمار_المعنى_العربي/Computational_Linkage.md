# الربط الحاسوبي
## Computational Linkage — Data ↔ Code ↔ Architecture

> هذا الملف يوثِّق **الربط بين البيانات الموجودة في الـ workspace والكود وبين المعمار الفلسفي/الإدراكي/اللغوي**.  
> هو **توثيق على المستوى الحاسوبي** بحسب `11_Abstraction_Levels.md`، ولا يُلغي ولا يحلّ محل المستويات الأعلى.

---

## القاعدة الحاكمة (مستفادة من `11_Abstraction_Levels.md`)

> **البيانات والكود يقعان في المستوى الحاسوبي. هما يخدمان المستويين اللغوي والإدراكي، ولا يستبدلانهما. كل سطر بيانات وكل سطر كود يجب أن يُقرأ بهذه القاعدة.**

ولذلك:
- جدول الجوامد ليس "تعريفًا فلسفيًا للجامد"، بل **خادمٌ تشغيلي** لتصنيف توكنات النص.
- جدول الأوزان ليس "نظرية اشتقاق"، بل **مرجع نمطي** لمطابقة سطح الكلمات.
- ملف الحروف الموحَّد ليس "تعريفًا دستوريًا للحرف"، بل **قاعدة بيانات** للحروف الكلاسيكية.

## خريطة الربط — Data → Code → Architecture

### 1) ربط الحروف

| المستوى | المكوّن |
|---|---|
| **حاسوبي — مصدر خام** | `data/Huruf_Maani_Five_Scholars_With_Ibn_Hisham.xlsx` (401 إدخال خام) |
| **حاسوبي — معالَجَة** | `huruf_maani_normalization/huruf_maani_unified_master.xlsx` (179 كيانًا موحَّدًا) |
| **حاسوبي — كود** | `src/architecture_test/huruf_loader.py` (Index + lookup) |
| **لغوي** | "الحرف" بالمعنى النحوي الكلاسيكي (الجرجاني، ابن هشام، الرماني، الزجاجي، سيبويه) |
| **إدراكي** | الحرف كـ Structural-Condition Inducer ضمن الأنماط الخمسة لـ State |
| **فلسفي** | الحرف بوصفه عاملًا يفرض شرطًا بنيويًا على الجملة (مستفاد من Q2 و `Q2_State_Test_From_Huruf.md`) |

**القاعدة:** اللوكب الحاسوبي يُرجع `HurufEntry`. هذا الـ Entry يحوي بيانات (canonical_form, fully_vocalized_form, category, ...). **لا يحوي** الدلالة الإدراكية أو الفلسفية. هذه تُستنتج لاحقًا في pipeline.

### 2) ربط الجوامد

| المستوى | المكوّن |
|---|---|
| **حاسوبي — مصدر** | `data/الجوامد.xlsx` — sheet `Jawamid_Classification` (20 تصنيفًا، 108 أمثلة) |
| **حاسوبي — كود** | `src/architecture_test/jawamid_loader.py` (Index + lookup) |
| **لغوي** | "الجامد" بمعنى الاسم غير المشتق (20 تصنيفًا فرعيًا: اسم ذات، اسم جنس، اسم علم، إلخ) |
| **إدراكي** | الكيان الذي يستقر بـ Identity إحالية، لا يحتاج اشتقاقًا (انظر `Distinction_Identity_vs_Continuity.md`) |
| **فلسفي** | عقدة استقرار جوهرية (بحسب تعريف Entity في `02_Core_Concepts.md`) |

**القاعدة الحاسوبية المهمة:** جدول الجوامد **ليس قائمة مغلقة**. الأمثلة فيه seed، لا حصر. غياب كلمة من الـ seed لا يعني أنها ليست جامدة — فقط أنها ليست في الأمثلة المُدرَجة. هذا منصوص عليه صراحة في docstring الـ loader.

**اكتشاف من الربط:** بعض كلمات الجدول تظهر في **عدة تصنيفات**:
- "من" → اسم موصول + اسم شرط + اسم استفهام
- "ما" → اسم موصول + اسم شرط + اسم استفهام
- "أي" → اسم شرط + اسم استفهام
- هذا يطابق ما اكتشفناه في `Q2_State_Test_From_Huruf.md` عن polyfunctionality.

### 3) ربط المشتقات

| المستوى | المكوّن |
|---|---|
| **حاسوبي — مصدر** | `data/Mushtaqat_Weights_Final_Corrected_With_Fa3l-minimall.xlsx` — sheet `الأوزان_المصححة` (80 وزنًا، 16 بابًا) |
| **حاسوبي — كود** | `src/architecture_test/mushtaqat_loader.py` (Index + pattern match) |
| **لغوي** | "المشتق" بمعنى الاسم المشتق من فعل: اسم الفاعل، اسم المفعول، الصفة المشبهة، صيغة المبالغة، اسم الزمان، اسم المكان، اسم الآلة، اسم التفضيل، إلخ |
| **إدراكي** | كيان يحمل **أثر حدث** أو **استمرار حدث** (الأنماط 1 و 2 من Q2: Event-Residue و Event-Continuation) |
| **فلسفي** | الكيان المشتق ≈ State من نمط Event-Residue/Continuation متجسد في صيغة اسمية |

**القاعدة الحاسوبية المهمة:** المطابقة الحالية **heuristic، لا parser**. تعتمد على هيكل الحروف الساكنة من الوزن (ف، ع، ل = wildcards) ومطابقتها بالكلمة. هذا ينتج:
- **مطابقات صحيحة** كثيرة (كاتب → فاعل، مكتوب → مفعول).
- **مطابقات متعددة** للكلمة الواحدة (عسر يطابق فَعْل، فَعِل، فَعَل — كلها صيغ مشبهة محتملة).
- **مطابقات خاطئة محتملة** (شجرة تطابق بعض الصيغ التي لا تنطبق عليها سياقيًا).

التعدد ليس عيبًا، بل **يعكس فضاء الاحتمالات** (متسق مع `07_Context_Probability_Resolution.md`). التمييز بين الاحتمالات يحتاج سياقًا، وهذا خارج نطاق المطابقة السطحية.

## خطوة Pipeline الجديدة (STEP 3.5)

أُضيفت خطوة `_step_word_classification` في `pipeline.py`، تطبق التقسيم الكلاسيكي **الكلام = اسم وفعل وحرف** على مخرجات التوكنزر:

```
لكل توكن:
  if huruf_match:            → harf
  elif looks_verbal:         → verb
  elif jamid_seed_match:     → jamid
  elif mushtaq_pattern_match → mushtaq
  else                       → unknown
```

**أولوية المطابقة دستورية:** الحرف يسبق الفعل، الفعل يسبق الجامد، الجامد يسبق المشتق. **سبب هذا الترتيب:**
- الحرف أوضح المرشحات (مطابقة قاموسية مغلقة نسبيًا).
- الفعل يحدد بمورفولوجيا واضحة (شكل الفعل).
- الجامد قائمة seed، فيتقدم على المطابقة النمطية.
- المشتق آخر لأن مطابقته heuristic وقابلة للتعدد.

**مخرج الخطوة يحوي:**
- `class_counts`: عدّاد لكل صنف.
- `per_token`: التصنيف لكل كلمة.
- `jamid_categories_seen`: التصنيفات الفرعية التي ظهرت.
- `mushtaq_babs_seen`: أبواب المشتقات التي ظهرت.
- `coverage_pct`: نسبة التوكنات المُصنَّفة (غير `unknown`).
- `layer_note`: تذكير صريح بأن هذا تصنيف حاسوبي يخدم اللغوي.

## القيود الحاسوبية الموثَّقة

### قيد 1 — الحدود مع شبه الحروف
"مَعَ"، "أَلْ التعريف"، التنوين — كلها فاعلة بنيويًا، **خارج Huruf dataset**. هذا قيد على البيانات، لا على المعمار. التوسعة تتطلب:
- إضافة "مَعَ" (والأسماء الظرفية شبه الحرفية) إلى dataset منفصل.
- إضافة "أل التعريف" و"التنوين" كعناصر مورفولوجية في خطوة معالجة مستقلة.

(هذا مسجَّل بالفعل في `09_Open_Questions.md` كنتيجة من `Architecture_Test_Sample_01.md`.)

### قيد 2 — التنوين والألف
كلمة مثل "يُسْرًا" تصبح بعد إزالة التشكيل "يسرا" (4 حروف بسبب ألف التنوين). الأوزان ثلاثية الحروف لا تطابقها. حلول ممكنة:
- إضافة قاعدة: إذا كان للكلمة تنوين فتح، استبعد الألف النهائية قبل المطابقة.
- (مؤجَّل).

### قيد 3 — Polysemy حقيقي
المطابقة النمطية تُعطي **تعددًا** (3+ بابات لكلمة واحدة). هذا **ليس خطأ**؛ يعكس الواقع اللغوي. التمييز بين البديل الصحيح يحتاج سياقًا، وهو **خارج نطاق المطابقة السطحية**. متَّسق مع `07_Context_Probability_Resolution.md`.

### قيد 4 — حدود heuristic للفعل
دالة `looks_verbal` في `tokenize.py` تعتمد على إشارات سطحية (بداية ي/ت/ن/أ + حركة، انتهاء بفتحة/سكون، إلخ). هذا **ليس parser صرفي**. ينتج:
- false positives على بعض الأسماء.
- false negatives على بعض الأفعال.
محل التحسين لاحقًا.

### قيد 5 — Jamid seed، لا lexicon
جدول الجوامد يحوي 108 مثالًا فقط. كلمة مثل "العسر" أو "محمد" قد لا توجد في الـ seed (مع أن "محمد" مُدرج كمثال للعَلَم). الـ lookup negative ليس قاطعًا.

## مبادئ الربط الحاكمة

1. **الكود يخدم البيانات، البيانات تخدم اللغة، اللغة تخدم الإدراك، الإدراك يخدم الوجود.** هذا اتجاه قاعدة `11_Abstraction_Levels.md` (قاعدة 1: اتجاه التقديم).

2. **لا يُلغي تصنيفٌ حاسوبيٌ تصنيفًا فلسفيًا.** "كلمة لم يصنفها الكود" لا تعني "كلمة بلا هوية فلسفية". هي فقط "كلمة لم تطابق أيًا من المصادر الحاسوبية الحالية".

3. **التعدد المتزامن مسموح.** كلمة قد تطابق عدة بابات (كاتب: اسم فاعل + اسم آلة)، أو عدة تصنيفات (من: اسم موصول + شرط + استفهام). هذا **ميزة**، لا عيب.

4. **الحدث الذي لا يطابق `looks_verbal` لا يعني انعدام Event-Continuation فلسفيًا.** ولكنه يعني أن **التصنيف الحاسوبي لم يلتقطه**. الفرق دستوري بحسب `11_Abstraction_Levels.md`.

5. **توسعة البيانات أولى من توسعة الكود.** الفجوات الحالية (مع، أل، التنوين) تُعالج بإضافة بيانات، لا بإضافة منطق.

## الأسئلة الفرعية الناشئة (تُسجَّل في `09_Open_Questions.md`)

- هل نضيف dataset مستقل للضمائر، الإشارة، الموصولات (كلها مبنيات اسمية)؟
- كيف يربط النظام بين الجذر والوزن لتحديد الباب الصحيح من المتعدد؟ (يحتاج محلل صرفي حقيقي.)
- هل تحتاج الأفعال dataset خاص بها (الأوزان الفعلية: فَعَلَ، فَعَّلَ، أَفْعَلَ، اِفْتَعَلَ، إلخ)؟
- كيف يُقاس "نجاح" الـ pipeline؟ هل نسبة coverage معيار كافٍ؟ أم نحتاج معيار correctness؟

## الخطوات اللاحقة الموصى بها (لا تُنفَّذ تلقائيًا)

- توسعة Huruf dataset بشبه الحروف (مع، عند، لدى، سوى، غير، نحو، إلخ).
- بناء dataset مستقل للمبنيات (الضمائر، الإشارة، الموصولات).
- إضافة dataset للأوزان الفعلية.
- اختبار الـ pipeline على Sample 02 (آية موسى والثعبان) لرؤية التغير حين يدخل فعل صريح.
- بناء معيار `correctness@N` لا `coverage@N` فقط.

**كل هذه الخطوات تقع في المستوى الحاسوبي.** لا تخل بالدستور، ولا تعدل القرارات المحسومة.
